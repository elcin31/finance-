# Supabase для FINLAB

Код поддерживает настоящий Supabase Auth (email/password) и PostgreSQL. Без двух публичных переменных окружения приложение работает в гостевом режиме. Оно не сообщает об успешной серверной синхронизации, если запрос завершился ошибкой.

## Настройка нового окружения

1. Используйте отдельный проект FINLAB. Не применяйте миграции к базам других приложений.
2. Скопируйте `.env.example` в `.env.local`. Укажите `NEXT_PUBLIC_SUPABASE_URL` и **publishable** key в `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Эти значения предназначены для браузера. `service_role`, `sb_secret_*` и пароль PostgreSQL здесь запрещены.
3. Примените SQL из `supabase/migrations/` по порядку. Для Supabase CLI сначала выполните `npx supabase --help`, затем `npx supabase link --project-ref <FINLAB_REF>` и `npx supabase db push`. Не добавляйте пароль базы в командную строку или Git.
4. В Authentication → URL Configuration укажите фактический Site URL. Добавьте `http://localhost:3000/profile` и адрес опубликованного приложения с `/profile` в разрешённые Redirect URLs. Для восстановления пароля используется этот же маршрут.
5. В Authentication → Providers включите email/password. Подтверждение email должно соответствовать настройкам приложения: регистрация с включённым подтверждением показывает сообщение о письме, а не объявляет пользователя вошедшим.
6. Для доставки писем реальным пользователям настройте SMTP и проверьте ограничения Supabase Auth. При стандартной почтовой доставке могут действовать ограничения адресатов и частоты запросов.
7. Перезапустите `npm run dev`. `NEXT_PUBLIC_*` также должны присутствовать во время Vercel build.

Таблицы находятся в закрытой схеме `finlab`. Добавлять её в Exposed schemas **не требуется**: приложение использует две функции в стандартной схеме `public` — `finlab_load_progress()` и `finlab_sync_progress(incoming jsonb)`.

## Применённая инфраструктура этой версии

Выделенный проект: `finlab-academy`, ref `iubwvalbydjxpvdmpocu`, регион `eu-central-1`. При создании инструмент Supabase сообщил стоимость проекта 0 в месяц. Лимиты и дальнейшие тарифные изменения определяются Supabase.

Миграция `finlab_initial` реально применена к этому проекту. Локальный файл создан командой Supabase CLI и затем переименован в timestamp, зарегистрированный удалённым migration API, чтобы история CLI оставалась согласованной. Исходный пустой файл был создан как `20261028082610_finlab_initial.sql`; применённая версия — `20261028082907_finlab_initial.sql`.

Следующая миграция `20261028083306_finlab_content_versions.sql` добавляет обратно совместимое поле `states.<lessonId>.contentVersion`. Она также реально применена. Старые документы без поля принимаются; новая версия — целое число 1…10000. При несовпадении с версией учебного контента приложение начинает новый run, не засчитывая ответы из старой редакции.

Миграция `20261028083525_finlab_attempt_content_versions.sql` сохраняет необязательную версию контента на каждой попытке. Исторические события не переименовываются и не перезаписываются. Состояния, настройки и сортировка событий сравнивают timestamps как реальные моменты времени; разные часовые смещения ISO 8601 не меняют порядок.

## Модель хранения

`finlab.progress_documents` — одна каноническая запись на `auth.users.id`. В JSONB находятся версия формата, настройки, позиции и черновики уроков, отдельные попытки ответов и завершения прохождений. Первичный ключ `user_id` одновременно даёт индекс для всех запросов прогресса. Удаление пользователя каскадно удаляет его запись.

Доступные владельцу представления имеют `security_invoker = true`: `profiles`, `learning_preferences`, `learning_progress`, `exercise_attempts`, `lesson_attempts`, `exam_results`, `review_queue`. Это проекции канонического документа, без копирования одних результатов в несколько таблиц. Освоение навыков пересчитывается в приложении из сохранённых попыток и версионированного учебного контента; отдельные произвольные проценты в БД не хранятся.

`finlab_sync_progress`:

- проверяет формат, типы, границы чисел, UUID, длины ответов и размер документа до 2 МБ;
- определяет владельца только через `auth.uid()`, без параметра `user_id`;
- блокирует запись через `FOR UPDATE`, поэтому параллельные синхронизации объединяются последовательно;
- объединяет попытки по UUID `attempt.id`, завершения по `runId`; повторная отправка гостевого документа не начисляет прогресс повторно;
- сохраняет уже записанный серверный результат при повторном UUID;
- выбирает более свежие позиции, черновики и настройки по timestamp;
- возвращает итоговый документ из базы как источник истины для аккаунта.

Клиент должен объединять полученный результат с ещё не отправленными локальными действиями и отправлять их следующим запросом. Черновик локально не означает, что он уже синхронизирован. Неподтверждённые изменения нужно сохранять отдельно до успешного ответа. Прогресс разных аккаунтов нельзя объединять автоматически; одноразовый перенос применяется к гостевому режиму.

Все таблицы защищены RLS по `(select auth.uid()) = user_id`. Для UPDATE есть и `USING`, и `WITH CHECK`. Функции работают с правами вызывающего пользователя (`SECURITY INVOKER`); `anon` и `PUBLIC` не имеют права их вызывать. Ключи администратора приложению не нужны.

Учебная проверка ответов детерминирована и выполняется в приложении. Собственные результаты в собственной записи не являются защищённым профессиональным сертификатом: клиентский прогресс не предназначен для соревнований, выдачи дипломов или проверки честности экзаменов. Чужие данные недоступны.

## Проверка защиты

Запустите `supabase/tests/security.sql` через SQL Editor под ролью postgres в отдельной FINLAB-базе. Он создаёт двух временных пользователей внутри транзакции, проверяет реальную RLS и выполняет `ROLLBACK`.

Проверки, выполненные на выделенном проекте 28 октября 2026:

- чтение и запись собственной записи;
- невозможность прочитать/изменить/вставить чужую запись;
- невозможность сменить владельца через UPDATE;
- изоляция представлений;
- запрет RPC для `anon`;
- дедупликация повторного импорта и сохранение серверной попытки при конфликте UUID;
- отсутствие повторного начисления завершения и сохранение новых ответов/черновиков при отправке устаревшего снимка другим устройством;
- совместимость legacy/versioned attempts и состояний, проверка границ версий, сравнение timestamps с разными часовыми смещениями;
- отклонение некорректных timestamps, типов и единиц структуры документа.

SQL вернул `PASS`; после отката тестовых записей осталось 0. Supabase Security Advisors вернул `lints: []`. Unit-тесты схемы в `src/lib/validation.test.ts` также проверяют ошибочные UUID, дубликаты, NaN/Infinity, границы и повреждённые документы.

`supabase/config.toml` создан текущим Supabase CLI для локального окружения PostgreSQL 17. Подтверждение email включено; локальные письма доступны через Supabase Inbucket после `npx supabase start`. Локальный Docker/PostgreSQL в рабочей среде этой поставки не запускался; попытка `migration list --local` получила `ECONNREFUSED`. Это не мешает выполненным проверкам на удалённом выделенном проекте.

Для проверки Auth через браузер нужны реальный допустимый email и настроенная доставка подтверждений. SQL-проверки RLS не заменяют проверку доставки почты и переходов по письму.
