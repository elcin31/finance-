# FINLAB 0.2: данные, синхронизация и экзамены

Обновление аддитивно. Исходные `finlab.progress_documents`, UUID попыток, версии контента, завершения и Auth-пользователи сохраняются. Никакие таблицы других проектов не используются. Выделенная база: `finlab-academy`, ref `iubwvalbydjxpvdmpocu`.

## Миграции

После трёх миграций 0.1 последовательно применяются:

1. `20261029090827_finlab_learning_v2.sql`: нормализованная практика, черновики, защищённый экзаменационный API.
2. `20261029090828_finlab_exam_bank_v2.sql`: первый неизменяемый банк серверных вариантов.
3. `20261030051743_finlab_exam_bank_complete_coverage.sql`: банк 3 с покрытием всех 16 финансовых навыков, включая права акционера. Банк 2 сохраняется для начатых попыток и истории.

Все шесть миграций реально зарегистрированы в выделенном проекте. Применение к другому Supabase без подтверждения принадлежности FINLAB запрещено. Схему `finlab` не нужно добавлять в Data API Exposed schemas: браузер вызывает обёртки в `public`.

Для новых изменений сначала `npx supabase migration new <name>`, затем проверка и применение только к FINLAB. Файлы банка не размещаются в `public/`. Воспроизводимая генерация полного текущего банка:

```sh
npm run exam:bank -- supabase/generated/exam-bank-v3.sql
```

Компактная миграция перехода с банка 2 воспроизводится флагом `--from-v2`. Нельзя редактировать уже опубликованные вопросы банка: UPDATE/DELETE запрещает trigger. Новые варианты требуют новой версии, а старые продолжают оцениваться своим ключом.

## Сущности

| Сущность             | Назначение и целостность                                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `progress_documents` | Канонический прогресс уроков 0.1: настройки, позиции, черновики, исторические завершения                                   |
| `learning_events`    | Неизменяемые попытки 0.2; PK `(user_id,event_id)`, индекс по пользователю и времени                                        |
| `practice_drafts`    | Один черновик на `(user_id,draft_id)`, session UUID, параметры, ответ и использованная подсказка                           |
| `exam_bank`          | Закрытые публичные условия и приватные ключи; PK `(module_id,bank_version,variant)`                                        |
| `exam_attempts`      | Владелец или hash гостевого секрета, уникальный request UUID, вариант, черновик, позиция, неизменяемый серверный результат |
| `exam_rotation`      | Отдельный счётчик вариантов по модулю и аккаунту; для гостей общий счётчик модуля                                          |

Связи с Auth имеют FK и каскадное удаление принадлежащих пользователю результатов. Индексы покрывают владельца, время, поиск активного экзамена и внешний ключ банка. Определения навыков и зависимости версионируются в `src/content/skills.ts`. Mastery, очередь повторений и рекомендации пересчитываются из фактической истории, не хранят произвольные проценты. Алгоритм: [knowledge-engine.md](knowledge-engine.md).

## Синхронизация практики

`finlab_learning_load()` возвращает канонические события, черновики и серверные экзамены текущего `auth.uid()`. `finlab_learning_sync(events,drafts)` принимает только события и черновики; параметра с клиентскими экзаменационными баллами нет.

- Событие сохраняется локально перед запросом. Сервер вставляет `(user_id,event_id)` один раз; повторная отправка или конфликтующий JSON не перезаписывают подтверждённую попытку.
- Черновики объединяются по действительному моменту ISO timestamp. Равное время сохраняет серверный вариант; более старый снимок другого устройства не откатывает новый ответ.
- Клиент объединяет ответ БД с действиями, сделанными во время запроса. Неотправленные изменения сохраняются отдельно для аккаунта и повторно отправляются при следующем действии, восстановлении сети, входе или ручном повторе.
- Гостевая практика переносится по UUID. Гостевой ключ удаляется после подтверждения всех его событий. Прогресс другого аккаунта не импортируется.
- История уроков 0.1 и более полные события 0.2 используют один ID попытки. Модель знаний не считает один ответ дважды.
- Статус «синхронизировано» появляется только после ответа настоящего RPC. Ошибка сохраняет локальную очередь и показывает её состояние.

Ключи браузера: `finlab.guest.v1`, `finlab.account.v1.<uid>`, `finlab.learning.guest.v2`, `finlab.learning.account.v2.<uid>`. Удаление данных сайта удаляет гостевую историю. JSON-экспорт в профиле содержит обе версии данных; автоматического импорта произвольных экзаменационных баллов нет.

Валидация ограничивает длины, UUID, единицы структуры, конечные числа, seed, сложности, известные компетенции и даты не более чем на пять минут в будущем. Неверный формат не становится первой ошибкой знания. Лимит клиентской загрузки: 20 000 событий, 256 черновиков, 2 000 результатов экзаменов и 3,5 МБ. До многолетней эксплуатации нужна пагинация/архивирование. В БД события уже нормализованы; накопленную историю не следует обрезать молча.

## Защищённые экзамены

Браузер получает только условия вопросов. `correct`, `expected`, `correctOrder`, подсказки и разбор до отправки не входят в payload. В экзамене нет кнопки проверки отдельного вопроса.

Публичные обёртки: `finlab_exam_start`, `finlab_exam_get`, `finlab_exam_draft`, `finlab_exam_active`, `finlab_exam_submit`, `finlab_exam_claim`. Все `SECURITY INVOKER`. Узкие внутренние функции `SECURITY DEFINER` находятся в закрытой схеме, с фиксированным `search_path=''` и явной проверкой `auth.uid()` либо гостевого секрета. Прямого клиентского доступа к банку, оценкам и счётчикам нет.

1. Старт использует request UUID. Повтор того же запроса возвращает ту же попытку только её владельцу. Следующая попытка получает следующий из 16 вариантов; после 16 варианты повторяются, а баллы не суммируются.
2. У гостя отдельный случайный UUID-секрет; сервер хранит его hash. Знание ID попытки не даёт доступа. Секрет не является публичной ссылкой и не выводится в UI.
3. Ответы и позиция сохраняются на устройстве немедленно и на сервере с небольшой задержкой. Незавершённая попытка аккаунта восстанавливается на втором устройстве через `finlab_exam_active`. Неотправленный локальный черновик сохраняется при временной потере сети.
4. Отправка блокирует строку попытки, проверяет ответы и вычисляет балл на сервере. Все восемь вопросов имеют равный вес, порог — ровно 80%. Доля экзамена в mastery отдельно учитывает сложность вопросов.
5. Первая завершённая отправка фиксируется. Повтор submit с изменёнными ответами или клиентским баллом возвращает прежний результат. После завершения черновик также неизменяем.
6. После сдачи раскрываются ответы, разбор, слабые навыки и рекомендации. В приложении результат приходит из RPC, а не из локального JSON.
7. Перенос гостевого экзамена требует `claim` с действительным секретом и настоящего входа. После переноса гостевой секрет перестаёт давать доступ. Повтор claim тем же владельцем безопасен.

Локальные `examResults` не считаются авторитетными при новой загрузке: аккаунт получает их из БД, гость — по серверной проверке сохранённых возможностей доступа. Подтверждённые зачёты добавляются только в вычисляемое представление пути; они не переписывают старый клиентский документ. Исторические зачёты 0.1 сохраняются с прежним порогом 70%, но не выдаются за защищённые 25% mastery нового экзамена.

Открытый репозиторий содержит задания, формулы и инструменты генерации. Серверное оценивание защищает от подстановки клиентского `score=100`; это учебная проверка, а не прокторинг и не профессиональный сертификат.

## RLS и фактические проверки

У событий и черновиков включены RLS и FORCE RLS, владелец определяется только через `(select auth.uid())`. Для UPDATE черновиков есть `USING` и `WITH CHECK`. События не имеют UPDATE/DELETE для клиента. Пользовательские `user_metadata` не участвуют в авторизации. Privileged keys отсутствуют в frontend.

На FINLAB 30 октября 2026 выполнен `security-v2.sql`: **PASS** для сохранения 0.1, RLS двух пользователей, дедупликации, LWW, ограничений дат, скрытого банка, защиты оценки, idempotent submit, ротации, черновика между устройствами, guest claim и отзыва секрета, точного порога 80. Проверка 384 ответов активного банка 3 дала 384 правильных результата серверного grader; старый банк 2 также 384/384. Тестовые SQL-пользователи откатываются.

Security advisor сообщает одно предупреждение конфигурации Auth: `auth_leaked_password_protection` отключён. Ошибок RLS advisor не сообщил. Дополнительная защита паролей по утечкам требует проверки настройки и тарифной доступности в Dashboard; платные функции автоматически не включаются.

Регистрация, email recovery и redirect URL используют настоящую Supabase-конфигурацию. Доставка писем и физическая PWA-установка не доказаны тестовым password login. Подробные границы — в [verification-0.2.md](verification-0.2.md).
